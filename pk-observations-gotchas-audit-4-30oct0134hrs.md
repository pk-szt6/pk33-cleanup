### 1.5 🔴 [OBS] [GOTCHA] `pcl_selfcron.sh disable` has a substring collision

`_ct_drop_tag` uses `grep -vF -- "$1"` — a **fixed-string** match. The drop tag for `zk-index` is `# pcl-selfcron:zk-index`, which is a **substring** of `# pcl-selfcron:zk-index-zdash222`.

Verified live:

    drop tag = "# pcl-selfcron:zk-index"
      allowed_drop would be: 3
      [comment(not effective)] # pcl-selfcron:zk-index
      [comment(not effective)] # pcl-selfcron:zk-index-zdash222   <- substring collision
      [EFFECTIVE]              # pcl-selfcron:zk-index

**Today it's harmless** (the colliding line is already a comment, and `zk-index-zdash222` is independently DEAD). But **if `zk-index-zdash222` is re-enabled while `zk-index` is live**, then disabling `zk-index` silently removes `zk-index-zdash222` too.

Worse: `allowed_drop` is computed with the same `grep -cF`, so the shrink guard counts 3 and **permits** it. The guard won't catch this.

**Mitigation:** disable longest-tag-first, and run `pcl_selfcron.sh verify` after each disable.

**Second opinion wanted on:** is this a bug worth fixing in `pcl_selfcron.sh` before the mass pause? A one-line change (anchor the tag, e.g. `grep -vF -- " ${TAG_PREFIX}${name}"` with a leading space) would make it safe. Right now every entry whose name is a prefix of another's name is at risk — and with 103 entries, are there other such pairs?

### 2.3 🟠 [OBS] The `intake.append()` O(n) rescan — a slow-burn CPU defect

`zcons1/ssot_engine/intake.py`:

- `append()` (line 69) calls `_scan_max_seq(f)` — a **full re-scan of the entire 91 MB `rc/intake.ndjson`** to find the next sequence number.
- `append_many()` calls `append()` once per event → 76 events = **76 full rescans**.

Measured: `append_many` of 10 events = **10.0 s**. One `_scan_max_seq` pass = **1.9 s**.

The file grows every run, so this **degrades monotonically**. `feed_rc.py` writes 76 events per run (37 SBU rows × 2 + 2), driven by `sau_keeper.sh` every 10 min.

**This is the root cause of the CPU burn in audit #1** — the two Python processes pegging a core each.

**The fix is small:** cache max-seq in memory, or derive it from the checkpoint. 76 rescans → 1.

### 4.2 🟠 [OBS] [GOTCHA] `disable` has no reason field

`cmd_disable` sets `state=DISABLED` and touches nothing else. The registry has no column for *why* a job was disabled. `purpose` and `charter` are the nearest fields, and `purpose` is left untouched by `disable`.

**Recommendation:** append the reason to `purpose` when disabling, so the registry itself carries the justification. Otherwise the human ledger is the only place it lives.

### 4.3 🟠 [OBS] The crontab has a shrink guard, and a deliberate mass removal needs an override

`crontab_write` refuses any write dropping more effective lines than declared:

    REFUSED crontab write on pk33: effective lines 99 -> 2 (allowed drop 0).
    SELFCRON_ALLOW_SHRINK=1 overrides for a deliberate mass removal.

Good news: `disable` is tag-scoped, so each call is bounded and **won't trip the guard**. A mass pause done as ~90 individual `disable` calls is fine. A hand-written bulk `crontab` rewrite is not.

### 4.4 🟡 [OBS] The selfcron runaway has happened before, on this exact family

efus3 commit `bc13b9fc5`:

> fix(selfcron): STOP a live runaway — **heal was pumping the crontab 1294 lines and climbing**
>
> 17 registry rows carried `sched="#PAUSED20260711 47 0 * *"` — a schedule cron cannot parse. `tagged_line` writes it verbatim, so each "healed" entry landed as a COMMENT: never runs, stays DEAD forever, gets appended again next tick. `install` checks for an existing entry; `heal` did not. `warden.sh` calls heal every 5 minutes.
>
> MEASURED: one heal run appended 13 lines. 288 runs/day = ~3,700 lines/day. History: 120 lines (20 Jul) → 137 (25 Jul) → **1,294** today.
>
> A repair verb that cannot recognise its own previous repair is not a repair verb, it is a pump.
>
> CRONTAB COLLAPSED: 1,294 → 148 lines.

Two guards were added. **The lesson generalises:** the cron subsystem on this box has already had a self-amplifying failure. Treat any bulk crontab operation as high-risk even though the current code has guards.

### 6.2 🟠 [GOTCHA] zprotocols' 19 dirty files are cron-staged, never committed

The `zctx-refresh` cron (every 5 min) runs:

    zctx.sh verify || (zctx.sh compile && git -C .../zprotocols add ctx && git -C .../zprotocols commit -qm '...' && git push -q github main)

It **`git add`s but the commit is inside the `||` fallback branch** — so on the success path (`verify` passes) the files are staged and left in the index. **They accumulate.** This is a latent inconsistency that will keep re-appearing after every "clean."

**Second opinion wanted on:** is the intended behaviour "compile → stage → commit → push" every time? If so the `||` grouping is a bug and the fix is trivial. If the intent was "only push when verify fails," then the staged files should be reset instead.

## 8. Method, limits, and what I did NOT verify

**Method.** All figures are direct `du` / `ls` / `stat` / `ps` / `git` / `sensors` / `sqlite3` output captured live on 2026-10-30. zsm1's checkers were **re-run**, not read from the doc.

**Limits — please read before treating any number as exact:**

1. **The `opencode.db` internals are an estimate, not a measurement.** A full `dbstat` scan and a full `sum(length())` both timed out (>5 min on a 64 M-page file). The 239 GB figure comes from **rowid-band sampling** (40 bands × 200 rows, avg 526 KB/row) extrapolated against the known row count, cross-checked against `PRAGMA page_count` (63,938,339 × 4096 = 261.9 GB, matching file size). **Row distribution is not uniform** — the sampled bands had a max of 96 MB — so the extrapolation could be off either way. The headline "244 GB in one file" is exact; the "239 GB of it is event table" is an estimate.
2. **`sensors` was sampled twice, both during active `graphify` runs.** The 89–100 °C figures are loaded values, not a resting average. No time series was taken.
3. **`pnpm test` was not re-run** in zsm1. The 945-passed figure is inherited from `RESUME-HERE.md` and unverified.
4. **The load average reading (24–28) was measured against an idle CPU and is misleading.** It was caused by process churn, not saturation. Zero D-state processes throughout. Don't use load average as the health signal on this box.
5. **Fork attribution was sampled, not traced.** I caught the churn sources (docker healthcheck execs, rabbitmq BEAM VMs, cron fan-out) but did not run `strace` or bpftrace to prove the top contributors.
